## 1. 目的

現状、Google で「V EFFECT」と検索すると LP が見つかり、AI からも V EFFECT 自体を尋ねれば提案される段階まで来た。次のステップは、**まだ V EFFECT の存在を知らない人**に、検索経由でリーチすること。

そのための入口として、LP にブログ（SEO記事群）を新設する。ただし v1 で想定していた「習慣化 コツ」のようなビッグキーワードでの正面突破は、調査の結果、新規ドメイン・一人運用という条件下では現実的でないと判断した（§3）。v2 ではターゲットキーワードと優先順位を再設計する。

## 2. 現状整理

### 2.1 LP の技術構成（`docs/landing_page_guide.md` より）
- 完全な静的 HTML + CSS。ビルドツール・フレームワーク・JS なし
- `public/index.html`（日本語）/ `public/en/index.html`（英語）の2ページ静的方式
- Firebase Hosting はマルチサイト構成。LP は target `lp`、デプロイは必ず `firebase deploy --only hosting:lp`
- SEO基盤は一定整備済み: `robots.txt`、`sitemap.xml`（現状5 URL）、hreflang、canonical、JSON-LD（`SoftwareApplication`）、OGP
- **Search Console へのサイトマップ送信自体が未着手**。今回が実質初回登録になる

### 2.2 アプリ内「ブログライクなコンテンツ」（`lib/screens/v_practice_screen.dart`）
- `DevBlogPost` モデル + Firestore コレクションを購読する、開発者からログイン済みユーザーへの運営告知機能（カテゴリ: 運営/ヒント/シーズンタスク）
- SEO記事とは目的も読者層も別物。参考にするのは黒×ゴールドのデザイントーンのみで、データ・Firestore接続は流用しない（v1と同じ結論）

### 2.3 【v2で追加】競合調査で判明したリスクと前提の再設定

計画を実行に移す前に、「このブログ施策で本当に成果が出るのか」を Web 調査で検証した。結果、当初の想定より難易度が高いことが判明した。

| 調査事実 | 出典・内容 |
|---|---|
| **想定キーワードは直接競合が既に押さえている** | 「習慣化 コツ」の実際の検索結果には、グロービス・ベネッセ・駿台に加え、**日本最大級の習慣化アプリ「みんチャレ」の公式ブログ**（専門家監修つき）が上位表示されている。新規ドメインの V EFFECT が同じビッグキーワードで正面から戦うのは著しく不利 |
| **個人開発のSEO単体戦略は失敗例が多い** | 個人開発者の実例では、4,000ページ近いコンテンツを作っても1日の検索流入は10件程度に留まったケースが報告されている。同事例は「需要検証」「個人ブランディング／SNS発信」の方が初動獲得に効くと結論づけている |
| **新規ドメインには構造的なハンデがある** | 新規ドメインは一般に成果が出るまで3〜6ヶ月、**競合の激しいキーワードでは1年以上**かかるとされる（サンドボックス期間）。veffect.web.app は2026-07-07リニューアルの若いドメインで、この点でも不利 |
| **個人メディアの定石はロングテール** | 開設したばかりでドメインが育っていないサイトがビッグワードで上位表示するのは難しく、競合の少ない複合キーワード（ロングテール）を積み上げてドメイン全体を育てるのが基本戦略。ロングテールはCVRが高いという利点もある |
| **ブログより即効性のある施策がある** | ASO（App Store Optimization）の改善だけで、オーガニックインストール+8%、CVR+10%程度の効果が報告されている調査がある。作業負荷もブログ執筆よりずっと軽い |
| **一方でブログ経由ユーザーの質は高い** | SEO経由（Web検索でアプリを知ってから来訪）のユーザーは、広告経由より LTV が2〜3倍高いというデータもある。ブログが無意味という結論ではなく、**即効性はASO、資産形成はSEO**という役割分担が実態に近い |

詳細な調査根拠・出典URLは本ドキュメント末尾の「調査ログ」参照。

## 5. `tool/generate_blog.py` の仕様（変更なし）

- 依存: `markdown`（Markdown→HTML変換）、`PyYAML`（frontmatterパース）
- 処理内容:
  1. `content/blog/*.md` を全件読み込み、frontmatter + 本文をパース
  2. 日付降順にソートし、各記事について `public/blog/<slug>/index.html` を生成
     - `<title>` / meta description / canonical / OGP（og:title, og:description, og:image, og:url）
     - JSON-LD `BlogPosting`（headline, datePublished, dateModified, author, image, mainEntityOfPage）
     - 本文末尾に「関連記事」2〜3本 + アプリDL導線（App Storeボタン、既存 `.store-button` を流用）
  3. `public/blog/index.html`（一覧）を生成。既存 `.features` / `.gallery` のカードデザインを踏襲
  4. `public/sitemap.xml` を全文再生成（既存5URL定義を保持しつつブログ記事URLを追記。`<lastmod>` は記事の `updated` から設定）
  5. 実行コマンドは `python tool/generate_blog.py` の1行のみ

既存 `generate_lp_images.py` と同じ「実行すれば `public/` が更新される」という体験に揃える。

## 6. 【v2で全面改訂】ターゲットキーワード設計

### 避けるキーワード
「習慣化 コツ」「習慣 続かない」「三日坊主 治す」など、単語1〜2語の一般語（ビッグワード）。理由は §2.3 の通り、みんチャレ等の強いドメインが既に占有しており、新規ドメインが1年以内に割り込む見込みが薄いため。

### 狙うキーワード（ロングテール、V EFFECT独自の切り口）
一般的な習慣化ブログが書いていない、V EFFECT のプロダクト構造（宣言 × 証明写真 × 仲間 × 勝敗）に紐づく複合語を優先する。

| 切り口 | キーワード例 |
|---|---|
| 宣言効果（行動科学） | 「宣言 習慣化 効果」「有言実行 アプリ 続く」 |
| 証明・記録による可視化 | 「習慣化 写真 記録 アプリ」「継続 証拠 モチベーション」 |
| 一人ではなく仲間と（ソーシャル・アカウンタビリティ） | 「習慣化 一人 続かない 仲間」「習慣化アプリ 友達と」 |
| 勝敗をつける設計 | 「習慣化 ご褒美より宣言」「三日坊主 対策 ゲーム化」 |
| 開発者の専門性（taVNS研究由来の行動科学・脳科学） | 「習慣化 脳科学 仕組み」「意志力 頼らない 習慣」 |

これらは検索ボリュームこそ小さいが競合が薄く、質の高い記事であれば新規ドメインでも上位表示のチャンスがある。加えて検索意図がV EFFECTの機能と直結しているため、CVR（記事読了→インストール）もビッグワードより高くなりやすい。

## 7. SEO実装ディテール（変更なし）

- 見出し構造: 記事タイトルは `<h1>` 1つ、本文は `<h2>` / `<h3>` で構成
- meta description は120字前後、キーワード詰め込みをせず自然文で書く
- 内部リンクを厚くする（sitemap頼みにしない二重の発見経路にする）:
  - LPトップのヘッダーナビに「ブログ」リンクを追加
  - 一覧ページ → 各記事
  - 各記事末尾 → 関連記事2〜3本、LPの機能紹介セクション（`#features`）への回遊リンク
- 画像を使う場合は `tool/generate_lp_images.py` と同じ方針（幅720px程度・WebP化）で軽量化する
- `aggregateRating` などデータのない構造化データは入れない

## 8. Google Search Console 再登録を回避する方法（変更なし）

### 結論
sitemap.xml を最初に1回だけ GSC に登録しておけば、以降は Googlebot が自動的に sitemap を再取得し、新規・更新 URL を検出する。ページを更新するたびに「URL検査 → インデックス登録をリクエスト」を手動で行う必要はない。

### 仕組みとして組み込むこと
1. **sitemap.xml の自動全再生成**（§5④）: 記事追加のたびに `<lastmod>` が更新され、Googlebot が差分を検出しやすくなる
2. **内部リンクの充実**（§7）: sitemap に頼らずクローラーがリンクを辿るだけで新規記事を発見できる経路も並走させる
3. **継続的な更新**: クロール頻度はサイトの更新頻度に応じて調整されるため、コンスタントな追加自体が反映速度を上げる
4. **（任意・低コスト）RSSフィード `/blog/feed.xml`**: Googleの直接的なインデックス速度には効かないが、他クローラーや将来のメール配信導線に転用できる
5. **IndexNow は見送り**: Bing/Yandex は対応済みだが Google は非対応

### ユーザーが行う作業（初回のみ）
1. GSC で `sitemap.xml` をサイトマップとして送信
2. `/blog/` と初回公開する数記事について「URL検査」→「インデックス登録をリクエスト」で初速をつける

以降は `python tool/generate_blog.py` → デプロイ、だけで完結し、GSC操作は不要になる。

## 9. 【v2で新設】このプランの外側にあるが、優先度が高いかもしれない施策

調査の結果、ブログより先に着手した方が費用対効果が高い可能性のある施策が見つかった。本ドキュメントのスコープ（LPブログ）には含めないが、実行判断の参考として明記する。

| 施策 | 概要 | アプリ本体の変更要否 |
|---|---|---|
| **ASO（App Store Optimization）** | App Store Connect 上のタイトル・サブタイトル・キーワードフィールド・スクリーンショットの最適化。ブログよりずっと軽い作業で、+8%オーガニックインストール／+10%CVR相当の効果が報告される調査がある | **不要**（ストア掲載情報の変更のみ。`lib/`配下のコードは変わらない） |
| **SNS/UGCによるバイラル化** | V EFFECT は「努力共有SNS」という構造上、達成投稿を外部SNS（X/Instagram等）にシェアできる導線があれば、Duolingo型のプロダクト主導グロースと相性が良い可能性がある | **要検討**（外部シェア機能の追加はアプリ側の実装が前提になり得るため、「アプリは一切変更しない」という本計画の制約と衝突する。実施する場合は本計画とは別に、アプリ変更を伴う独立した計画として起案する） |

本計画（LPブログ）はこれらと並行、または後追いで進めても矛盾しない。ただし着手順としては ASO → ブログ の順を推奨する（ASOはコストが低く、アプリ非変更で即着手できるため）。

### 10.3 著作権配慮（重要）

5記事はいずれも `James Clear『Atomic Habits（複利で伸びる1つの習慣）』` または `Tim Ferriss『Tools of Titans（シリコンバレー式超ライフハック）』` の内容紹介を軸に構成されている。アプリ内お知らせ（ログイン済みユーザー限定）として運用してきた分にはリスクが顕在化していなかったが、**不特定多数がGoogle検索経由で到達する公開Webページ**として出す場合は、著作権法上の「引用」の要件（明瞭区別性・主従関係・必要最小限の引用範囲）を満たしているかを個別に見直す必要がある。

編集方針:

1. **要約部分を圧縮し、独自解説・V EFFECTでの実践方法を主にする**。特にリスク「高」の `u0NvxFHr3JrhxDRIQQNa` は、書籍の要約という体裁をやめ、「自己理解を深めるための問い」というテーマ部分のみを踏襲し、大部分を書き下ろしに近い形でリライトする
2. **直接引用は1〜2文以内に絞り、`<blockquote>` + 出典（書籍名・著者名・章）を明記**する（既存記事は末尾に出典を記載する慣習が既にあり、これは踏襲する）
3. 上記の編集を経ても懸念が残る記事は、**公開を見送るか、V EFFECT側のオリジナル要素（アプリの利用データや行動科学の一次情報）の比率をさらに高めてから公開する**

この編集作業自体は次の実装フェーズ（Markdown原稿の起こし）で行う。本ドキュメントでは方針の明記に留める。

### 10.4 日英同時公開の検討

確認の結果、5記事すべてに英語本文（`bodyEn`）が既に用意されていた。v1/v2では「フェーズ1は日本語のみ」としていたが、翻訳コストが実質ゼロであるため、**日本語版の編集が固まった段階で英語版（`/en/blog/`）も同時に検討する**。ただし英語版はURL構造・hreflangの追加設計が必要になるため、コスト増を理由に日本語版を優先し、英語版は基盤(§4〜5)が安定してから着手する（フェーズ1.5として後述）。

## 13. 変更しないもの（影響範囲の明示）

- `lib/` 配下の Flutter アプリコード（`v_practice_screen.dart` を含め一切変更しない）

- デプロイ対象は引き続き `--only hosting:lp` のみ

## 14. リスク・注意点（v3で更新）

- **著作権リスク（新規・重要）**: 初速コンテンツとして採用する5記事は Atomic Habits / Tools of Titans の内容紹介が中心。§10.3の編集（要約圧縮・独自解説追加・引用の最小化）を経ずに原文のまま公開しない。編集後も懸念が残る記事（特に `u0NvxFHr3JrhxDRIQQNa`）は公開順を後回しにするか、独自性を高めてから出す
- **ビッグキーワードでは1年経っても上位表示しない可能性がある**。§6のロングテール戦略に沿ってもゼロ流入のリスクは残る前提でKPIを設計する（例: 検索順位ではなく「記事本数」「インデックス数」「ロングテールでの部分的な上位表示」を短期KPIにする）
- 記事の質が低いと「作っただけ」で終わる。GSCの検索パフォーマンスで実測しながら継続する運用が前提
- キーワード詰め込みなど過度な最適化はGoogleのスパム判定リスクがあるため、読者本位の文章を優先する
- `/blog/` 配下は日本語のみのため、hreflang は既存2ページ（`/` `/en/`）とは別扱いとする
- 記事に画像を使う場合は必ずWebP化・軽量化する
- **ブログ単体に集客を依存しない**。§9のASO等、アプリ非変更で着手できる即効性のある施策と並行させることで、ブログの成果が出るまでの期間のリスクをヘッジする
