# ロールモデル機能 設計書

本ドキュメントは、V EFFECT プロジェクトにおいて他のユーザーを「ロールモデル（目標とする人）」として登録し、そのユーザーの努力（タスク達成状況や投稿履歴）を参考にできる「ロールモデル機能」の設計書です。

開発メンバーの renn さん（初学者）にも分かりやすいよう、専門用語には括弧書きで説明を添えています。

---

## 1. 機能概要

ロールモデル機能とは、他のユーザーを「ロールモデル」として登録し、そのユーザーの毎日のヒーロータスク（習慣化したい目標）の達成状況や、これまでの投稿履歴を確認できる機能です。自分より先に行っている人や、憧れの人の努力を可視化することで、自身のモチベーション維持につなげます。

---

## 2. UI/UX設計（画面遷移と操作フロー）

### 2.1 画面遷移フロー

ロールモデルの登録からアクティビティ確認までの遷移は以下の通りです。

```
[Vタイムライン（タイムライン画面）]
       │
       ▼ (アバター画像をタップ)
[ユーザープロフィール（他人のプロフィール画面）]
       │
       ├─► 【新規ボタン】「ロールモデルに登録」をタップ ──► ロールモデル登録完了
       └─► 【新規ボタン】「ロールモデルから解除」をタップ ──► ロールモデル解除完了
       
[マイプロフィール（自分のプロフィール画面）]
       │
       ▼ (「ロールモデル一覧」ボタンをタップ)
[ロールモデル一覧画面（新規画面）]
       │
       ▼ (ロールモデルをタップ)
[ロールモデル詳細・アクティビティ画面（新規画面またはプロフィール画面の拡張）]
       │
       ├─► 週間タスク達成率（過去7日間の達成グラフ）を表示
       └─► 過去の投稿履歴（カレンダー表示またはタイムライン表示）を表示
```

### 2.2 主要画面のデザイン

#### ① ユーザープロフィール画面（他人のプロフィール）の拡張
* **変更点**: 
  * フォローボタンの下部（または横）に、**「ロールモデルに登録」**（または星マークなどのアイコンボタン）を追加します。
  * 既に登録されている場合は**「ロールモデル解除」**ボタンに切り替わります。
* **初心者向けアドバイス**: 既存の `UserProfileScreen` (`lib/screens/user_profile_screen.dart`) のレイアウト崩れを防ぐため、ボタンの配置には `SizedBox` や `Padding` を使って余白を調整します。

#### ② ロールモデル一覧画面（新規作成）
* **機能**: 
  * 自分が登録しているロールモデルの一覧をリスト形式で表示します。
  * 各項目には、アバター画像、表示名（displayName）、現在の継続日数（streak）、および「今日のタスク完了数（例: 2/3完了）」を小さく表示します。
  * リストをタップすると、そのロールモデルの「アクティビティ詳細」へ遷移します。

#### ③ ロールモデルアクティビティ詳細画面（新規作成または拡張）
* **機能**:
  * **週間タスク達成率**: 過去7日間の各日の「完了したタスクの数 / 設定タスク数」を棒グラフやパーセンテージでビジュアル表示します。
  * **投稿履歴**: ロールモデルが過去24時間以内に投稿した画像や、過去の努力ログを一覧で確認できます。

## 3. Firestore スキーマ設計

ユーザーごとのロールモデルの関係は、Firestore（ファイアストア：Googleのクラウドデータベース）に保存します。

### 3.1 リレーション（データ構造）の設計比較

ロールモデルの関係性をどのようにデータベースへ保存すべきか、2つのアプローチを比較します。

| 設計案 | 構造 | メリット | デメリット |
| :--- | :--- | :--- | :--- |
| **案A（採用）**<br>サブコレクション方式 | `users/{uid}/role_models/{targetUid}` | ・ユーザーごとのロールモデル一覧を高速に取得できる<br>・セキュリティルールがシンプルに書ける（自分のフォルダしか見せない制限が簡単） | ・「自分をロールモデルに登録している人」を逆引きで探す際に、コレクショングループクエリ（データベース全体を横断検索する仕組み）が必要になる |
| **案B**<br>ルートコレクション方式 | `role_models/{relationshipId}` | ・「AさんがBさんを登録」「Bさんを登録している人全員」の双方向の検索（クエリ）が容易 | ・複合インデックス（複雑な並び替えや条件検索に必要な索引）の設定が増える<br>・セキュリティルールが複雑になりやすい |

**決定**: **案A**を採用します。V EFFECTでは、「自分が誰をロールモデルにしているか」を表示することが主な用途であり、セキュリティ的にも自分のサブコレクション (子どものデータの集まり) として完結する方が安全で設計がシンプルなためです。

### 3.2 具体的なデータ構造

#### コレクションパス: `users/{uid}/role_models/{targetUid}`

各ロールモデルドキュメントには、以下のデータを保持します。

| フィールド名 | データ型 | 説明 |
| :--- | :--- | :--- |
| `targetUid` | `String` | ロールモデル対象ユーザーのUID（ユーザー識別ID） |
| `createdAt` | `Timestamp` | ロールモデルに登録した日時（Firestoreのタイムスタンプ） |
| `displayName` | `String` | 対象ユーザーの表示名（キャッシュ用：画面表示を高速化するため） |
| `username` | `String` | 対象ユーザーのユーザー名（キャッシュ用） |
| `photoUrl` | `String?` | 対象ユーザーのプロフィール画像URL（キャッシュ用、未設定時はnull） |

> 💡 **キャッシュ用フィールドについて**:
> 表示名やプロフィール画像をこのドキュメントに保存（キャッシュ）しておくことで、一覧画面を表示する際に対象ユーザーのドキュメントを毎回1件ずつ読み込む必要がなくなり、読み込み回数（Read数）を大幅に削減してアプリの動作を軽くできます。

## 4. ロールモデルの「タスク達成率」計算ロジック

ロールモデルの活動度を示す「タスク達成率」の計算方法について検討します。

### 4.1 計算方法の比較

| 方式 | 設計概要 | メリット | デメリット |
| :--- | :--- | :--- | :--- |
| **方式1（採用）**<br>クライアントサイド<br>（アプリ側）動的計算 | 1. 相手の `AppUser` からタスク一覧を取得。<br>2. 相手の `posts` (投稿コレクション) から該当日の投稿を取得。<br>3. アプリ側で一致するタスク数を数えてパーセンテージを算出する。 | ・追加のデータ更新処理が不要（バグが起きにくい）<br>・常に最新のリアルタイムな達成率が表示できる | ・過去数日分のデータを表示する際、取得する投稿ドキュメントの数が増える（Firestoreの読み込みコスト増） |
| **方式2**<br>日次統計データ保存方式 | 1. ユーザーが投稿したタイミングで、Cloud Functions（サーバー側プログラム）がその日の達成率を計算。<br>2. `users/{uid}/daily_stats/{date}` ドキュメントに完了数を保存しておく。 | ・閲覧時は1つのドキュメントを読むだけで済むため、読み込みが非常に高速でコストが安い | ・投稿の作成・削除時に統計データを正確に更新し続けるロジックが必要になり、開発難易度が上がる |

**決定**: **方式1**を採用します。V EFFECTは現在Firestoreのドキュメント件数がそれほど大きくなく、クライアントサイドでの動的計算のほうが開発が簡単（rennさんへの負担が少ない）で、データの不整合（実際の投稿と統計データがズレるバグ）が発生しないためです。

#### 具体的計算式（例）:
$$\text{ある日の達成率} = \frac{\text{その日に投稿された固有のタスク数}}{\text{そのユーザーが設定しているタスク総数}} \times 100$$
（※例えばタスクが3つあり、そのうち2つのタスクに関する投稿が今日行われていれば、達成率は $2/3 = 66.7\%$ になります）

## 6. 実装に向けてのアドバイス（rennさん向け）

1. **まずは Service Layer (サービスレイヤー) から作成する**:
   UIを作る前に、`RoleModelService` を作って簡単なダミーの登録・解除ボタンでデータベースに正しく書き込めるかテストするとスムーズです。
2. **既存の UI パーツを再利用する**:
   ロールモデル一覧画面のリスト表示は、フレンド一覧画面 (`lib/screens/friends_screen.dart` など) のリスト表示コードを参考にすると、デザインの統一感が保てます。
3. **トランザクション (複数の処理を1つにまとめる仕組み)**:
   もしロールモデルを登録した際に、相手に通知を送るなどの追加処理を行う場合は、データの整合性を守るために `WriteBatch` (ライトバッチ) や `Transaction` (トランザクション) を使いましょう。
